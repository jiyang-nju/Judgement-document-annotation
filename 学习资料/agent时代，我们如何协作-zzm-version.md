关于协作，我也还只是一个初学者，大家多提提意见，一起想办法，把这个协作做好。


### 关于如何在github上协作

你需要做一些前置准备：
（注：不需要不需要记忆很多的指令，也不需要很理论化。1.2.需要你同时推进，而不是先学会一个再学会另一个）

1. 你需要了解git协作的工作流 、git指令。

重点：学会如何使用git --help，学会耐心查看报错信息而不是直接丢给ai。

具体要了解什么：不止是git clone / git add / git commit ，而是如何与remote远端建立映射关系，如何创建分支、如何转到分支上、如何fetch远端最新分支，如何处理远端现有分支和本地代码冲突问题、初次push分支需要setupstream等等，了解这些git指令具体在远端github和本地上干了什么，我们为什么要在branch上开发等等这些基础的前置知识。
（这块你们就看看过就行，在具体的开发中会慢慢遇到的，不急）

2. 你需要了解github panel中一些基本功能，学会如何建repo，熟悉repo面板的基本组成，学会在哪里pr，了解为什么要pr，以及之后如果遇到merge conflict如何解决（这个先不急）。

#### 学习建议：实践！

1. 自己创建一个 GitHub Repo → clone 到本地 → 修改 → commit → push

2. 自己创建一个非空的本地仓库 → 关联 GitHub remote → push 到远端

3. 在本地创建 branch → 在 branch 上开发 → push 到远端 → 在 GitHub 上创建 PR → merge

4. 尝试从 GitHub 获取远端最新代码，观察本地 branch 和远端 branch 的变化

等等

这个过程中最重要的还是**学会如何使用git --help，学会耐心查看报错信息而不是直接丢给ai。**


### 关于在ima上协作

ima上，我们会放一些**重要通知**和**归档学习资料**。大家在自己探索中遇到关于项目开发的资料之后，需要先大致看过一遍，觉得确实有价值之后，再放上来（这是大家互相扶持的重要步骤，也为减轻大家理解力负债提出了这个要求）。

定期组会，每人需要准备的报告内容也提前放在这里。每次组会的分工和后续计划也写在这里。

在开发过程中，如果突然你想到特别有意思的点，请写在ima的**idea文档**中。请**新建一个文档，将编写日期写在开头，标题简单介绍idea和负责人**,可以先只是一个idea而没有实际代码改动。**你需要在每次组会之前，重新思考、打磨并整合你个人的这些ideas，在下一次组会的idea part提出**。非紧急情况，请**不要在群聊中提出**（因为我还会是觉得qq的聊天过于轻娱乐化了，我们无法深入交流这些很棒的ideas。并且考虑到当组员发送一则有价值的消息的时候，其他组员会认为有必要及时回复，而现实是我们经常有自己的安排，这样势必会打乱我们自己的节奏，也给我们带来一些心理压力，而我希望我们的合作是自由的）但，大家可以在文档中交互，对他人的想法提出意见，这个我很支持！

大家在开发中也会时不时踩坑，虽然当时会很恼火，但请耐心把这个**踩坑-解决**的过程记录下来，写在个人的ima文档下！这是非常宝贵的试错资料，对于我们复盘自己的行为模式和后续提升有很大的意义！！

### 关于分工

这个还没决定哎感觉是一件特别难办的事情。灵活岗位会在项目初期很有帮助，大家对项目的每个部分都有参与，不需要很多的交流成本，项目开发进度会很快，用户体验和产品功能也会很全面。但是在项目越来越大时，如果遇到我今天这种情况就很难办。每个模块（前端/后端）需要专人负责，遇到有他的部分要做修改，就需要把需求丢给这个人，让他实现，这样需要每个人都高度负责，而且每个人的理解不同，沟通成本会大大增加。很难办啊。


### 关于开发中必须遵循的约定


#### 概述：关于文档撰写

在实际开发中，我们需要撰写很多文档来解释我们负责的部分（docs: spec \ plan \ 接口契约 等等）往往会分散在项目的各处，难以收集、整理。在开发之前我们需要做以下约定：

1. 先清楚我们需要写什么。
**什么信息应该记录、记录在哪里、由谁维护、在改动代码之后如何更新**
原则上项目文档同意放置在docs/文件夹下，大致的结构如下：

```text
docs/
├── README.md
├── architecture.md
├── api/
├── schedule/
├── spec/
└── plan/
```

在实际的项目进行时会根据具体的内容做调整，以及进一步前后端分隔（如果是做前后端分离的架构的话）

关于哪些信息应该放哪类文档中，在这里做一个简单的解释：

| 信息                                  | 推荐位置               | 作用     |
| ------------------------------------- | --------------------- | -------- |
| 项目是什么、如何快速启动                | README                | 项目入口   |
| 具体细节                              | README / docs          | 开发环境   |
| 整体架构                              | `docs/architecture.md` | 建立项目地图 |
| 前后端接口                            | `docs/api/`            | 模块之间协作 |
| 开始做一个重要功能之前，先说明“要做什么”| `docs/spec/`           | 为什么这样做 |
| 在明确“要做什么”之后，写具体实现计划    | `docs/plan/`           | 记录重要选择 |
| 具体修改                             | github PR              | 这次改了什么 |
| 代码为什么这样写                      | 注释                    | 局部解释   |
| 想出一个很棒的点子可以                 | ima文档                    | 文档深度沟通   |

2. 文档撰写的要求
使用过superpower的大家都知道，ai自主生成的spec/plan可读性不大，一旦文件堆叠可能造成理解困难，可能你自己写的过一段时间也不知道，这块功能改动到底改了什么，版本控制也难做。我个人的经验是，**也许可以把这一轮你的prompt放在ai写的spec/plan文档前面，**（根据实际的情况稍稍修改prompt。），可回溯。

#### 概述：关于开发流程

(这块可能要依赖于67的要求，之前使用superpower感觉实现效果不错，但，人的决策占比太少了，不利于我们初级工程师的成长，所以我们需要有意识地多理解、多设计、多提出想法、多进行与ai与队友的技术讨论。不仅讨论怎么做还要多交流：**为什么他是这么想的，他的思维链是什么样的**！！元认知很重要！！)

#### 具体开发中，你要做什么：

1. 你需要在每次开发前，先**手绘**自己想要实现的功能（你实现的部分需要哪些数据？这些数据是如何在项目架构中/前后端+服务器中流动的？它们是什么形式传输的？接受和传递的api是什么…………）都需要详细地写出，直到你可以根据这幅图，详细地解释你实现了什么，这样就可以停止绘图了。其他形式也可以接受，但前提不变——”可解释“。这个阶段希望你可以真正参与进来，做重要决策，ai可以作为辅助。

2. 在开发过程中，你会根据ai的建议，有取舍地调整设计。在确定方向之后，可以自行手搓/ai编码。在修改代码的同时，不要忘记更新接口契约等文档。
其中，不单是在开发中与agent的交互，你在日常使用ai的时候，也需要慢慢刻意训练自己的prompt，学会用文字/图示清晰表达自己的需求。

3. 你需要在每次开发完成之后，在文档中，写done-list,**要求尽可能手搓完成**。
**每个人**在**每个开发阶段**维护**一份**done-list，最新的记录写在最开头，每次开发前让agent读取自己/他人的done-list，以便了解团队/自己的进展。

你需要的撰写格式如下：

>我实现了什么功能？（侧重项目整体）
>我的设计思路是什么？（侧重为什么这样设计）
>我的具体实现链路是什么样的？（侧重项目中如何实现这个模块的）
>我做了什么修改？牵扯到哪些模块？这些模块有哪些变动？我是否更新了这些模块的接口契约以及相关说明文档？（侧重代码层面）
>我留了哪些接口方便联调？我是否已经把这些数据成功对接上了前后端？如果没有，我下一步需要接上哪些数据，它们在哪些地方？(便于下一次开发和联调)

4. 你需要确保你负责的部分是可解释的，你可以对你的架构和代码全权负责（至少可以知道如何扩展、如何修改）。vibe coding会带来越来越多的理解力负债，所以请确保你的开发遵循“人工设计+ai纠偏”的原则，尽量不要让ai来负责架构的全部，这样可能会带来理解力负债难以偿还的后果。 

### 关于组会

我的想法是轮流主持，尽可能调动积极性。毕竟如果只是一个pm在输出是一件很心累的事情，也会占用pm很多时间，而且虽然团队才4个人，但是大部分人都是有惰性的（我就是喜欢偷懒的人）。我可以先来试试，但是希望大家都积极参与，因为这是我认为一个**非个人开发者必备的一项技能**，而且**在团队协作困难的大环境下，是一个很核心的竞争力**！！（上学期我们这个组商业需求的pm就做的很好，组员也都积极配合）

关于如何交流，每个人在组会中汇报什么：

1. 详细讲解自己的done-list，期间接受其他组员的query,不一定说要什么都答得上来，但是需要你有**尽可能让他人理解**的意识。这里需要你注意，讲述done-list是为了项目进展同步，最理想的目的是，让组员在听了你的讲解之后就理解你做了什么，落实到项目具体结构中是具体如何实现的（可以非代码层面，只是了解在那个文件中用哪个函数实现了什么），以及最重要的是，你这么做的思路（让我们知道你的思考过程）。这里不需要摒弃ai，可以提供你是如何和ai交互的，最后你是根据什么做出决策的等等）

2. 准备后续开发的ideas 。需要保证至少你对未来的项目有自己的规划，不做量的要求。每人都需要做分享。分享时，需要你大致讲讲，设计理由、功能、涉及的板块等。在idea part中大家积极讨论这些ideas的利弊和可行性，也可以现场与ai聊一聊。做好跨模块对接工作！！

3. 日常分工，明确每个人需要做什么，每人撰写自己的计划，写在**ima**中，**当期主持做汇总后在ima留档，再将文档移入项目 docs/schedule**




### 关于之前协作中遇到的问题

1. 多人协作开发时，每个人通常只负责很小的一部分，一种常见的分工就是前后端分工。但实际开发中经常会发生：我负责前端的一个功能，但是这个功能需要后端提供一个新的数据。于是如果后端这部分是别人实现的，我就不得不重新阅读他的代码，导致我本来只要做一个小功能，但为了可解释，我需要读懂很多其他不是我负责的东西。而且当项目做到后期，雨来越大时，这个问题是很严重的。

2. 在qq群中提出idea和project plan，而没有共享文档工作区，导致交流困难，且给组员带来心理压力。

3. 文档乱堆，在根目录下写文档，在前端后端写文档，这些我在之前都干过。。。导致项目很乱很乱

4. 组会大家都等组长汇报，汇报完我们也没听懂什么，也因为汇报的人没让我们实际上很好的理解（线上会议的弊端），也提不出什么有效的意见。开完组会后，依然依靠qq群交流，自己做自己的，功能会冲突，经常会有merge confilct还得修修修。
